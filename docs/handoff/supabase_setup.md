## 1. Supabase 현황과 세팅 메모

- 계정 조직: NFULL07's Org. 기존 프로젝트는 `mine-study`(서울 ap-northeast-2, 2026-07 생성, 일시정지 상태) 하나뿐이고 청년픽용이 아니다. **청년픽용 새 프로젝트를 만들어야 한다** (2026-11-12 확인).
- 리전은 서울(ap-northeast-2)을 제안한다.
- 무료 플랜은 1주 동안 쓰지 않으면 일시정지된다(기획서 위험 항목). 시연 전 활동 유지, 또는 그 달만 Pro를 검토한다. **비용이 생기는 설정은 주완 확인 후에만.**
- 스키마 변경은 Supabase CLI 마이그레이션 파일(`supabase/migrations`)로 남기고 Git으로 관리한다. 원격 DB를 대시보드에서 직접 고치는 방식은 피한다.
- 테이블 확정 후 TypeScript 타입을 생성(`supabase gen types`)해 프론트에 공유한다.
- pgvector: 임베딩 모델이 정해진 뒤 그 모델의 벡터 차원에 맞춰 컬럼을 만든다. 모델 미정 상태에서 차원을 임의로 정하지 않는다.
- Supabase는 해외 사업자 서비스라 개인정보처리방침에 처리위탁 사실을 적어야 할 수 있다. 범위는 미확인(법률 검토 필요).

## 2. 테이블 설계 방향 (제안, 미확정)

기획서 기준 데이터는 정책 쪽 3종(공고, 판정 규칙, 제출서류)과 사용자 쪽 1종(개인화 항목)이다. 아래는 그에 맞춘 최소안 **제안**이며, 주완 확인 후 확정한다.

| 테이블(제안) | 한 행의 의미 | 메모 |
|---|---|---|
| `policy` | 연도와 무관한 정책 단위 (후보 ID A1~H1, X1~X10) | 정책명, 운영기관, 목적 묶음(A~H), 지역 단계(중앙·충남·천안·아산) |
| `policy_notice` | 특정 연도·회차 공고 한 건 | API `plcyNo`(있으면), 접수기간, 접수 상태, 원문 URL, 수집일. API에 없는 7건은 수기 입력 |
| `source_document` | 근거 문서 한 건 (공고·첨부·FAQ·보도) | URL, 확보일, 확인수준(공고원문 / 기관 안내 / 2차출처 등) |
| `eligibility_rule` | 공고에 연결된 조건 하나 또는 조건 묶음 | jsonb 조건, 근거 원문 위치, 검수 상태(초안 / 검수 완료). 화면은 검수 완료만 사용 |
| `policy_relationship` | 두 공고 사이 관계 한 건 | 관계 상태 5종, 근거 문구, 검수 상태 |
| `document_requirement` | 공고별 제출서류 한 건 | 서류명, 발급처, 발급 경로 |
| `user_profile` | 사용자 기본 저장 10개 | `auth.users` 연결, RLS로 본인만 읽기·쓰기 |

- 공개 정책 테이블: 읽기는 공개(anon select), 쓰기는 service_role(적재 스크립트)만.
- AI가 만든 조건 초안은 검수 상태로 구분해, 검수 전 데이터가 판정에 쓰이지 않게 한다.
- API 원본 응답 보존용 테이블(예: jsonb로 레코드 통째 저장)을 둘지는 주완 결정.

### 적재 때 처리할 품질 문제

1. 천안 지역코드: 천안시 단독 정책은 44130만(113건), 광역·전국 정책은 44131·44133(827건)을 쓴다. 한 정책에 섞인 경우는 0건. 천안 사용자는 세 코드 모두와 매칭한다.
2. 연령 제한 플래그 `sprtTrgtAgeLmtYn`이 실제 연령 값과 맞지 않는다(3,969건 중 'N'인데 값 있음 2,116건, 'Y'인데 값 없음 1,030건). 연령은 최소·최대 값만 쓰고, 0은 제한 없음으로 보되 원문과 대조한다.
3. 소득 코드가 '무관'인데 문구에 소득 기준이 있는 정책 51건. 소득 코드만으로 O 처리하지 않는다.
4. 묶음 레코드 20260504005400113115('인재육성사업 추진')에 9개 사업(A2·B2·B3 포함)이 묶여 있고 코드가 모두 '기타'다. 원문으로 정책별로 나눈다.
5. 한 정책에 레코드가 여러 개: A1(등록금·생활비), C1(국토부·충남), F1(1차·2차), F2(전국·충남), G2(2025 두 건). 연도·회차·운영 주체를 구분해 별도 공고로 둔다.
6. API 기간·상태와 원문 불일치: D5(API 3.1~12.31, 원문 4.1~4.17), D4(API 상시, 원문 10.14 마감). 원문 우선.
7. 이전 연도 레코드만 있음: D2·E5(2025 등록, '마감'), G2(2025만). 2026 운영 여부 미확인으로 표시한다.
8. C2의 API 레코드명 '청년전용 저리대출상품 운영'이 버팀목과 같은 상품인지 확인 필요.
9. F2 전국 레코드 안에 '중위소득 100% 이하'(추가자격)와 '50% 이하'(소득기타)가 함께 적혀 있다.
10. C3 새 제한 문구(API 원문): "유사한 사업(대출이자 사업 등)으로 지원받고 있는 경우 지원 불가". 관계근거에 반영 필요.

## 4. 작업 순서 (제안)

각 단계가 끝나면 실행한 확인과 결과를 적는다. 실행하지 않은 확인은 "미실행"으로 쓴다. ★ 표시는 주완 확인을 받고 넘어간다.

0. **저장소 확인**: 폴더 구조, 프론트 위치·프레임워크, 기존 Supabase 관련 코드와 환경변수 이름, 실행 방법. 기능을 실제 동작 / 가상 데이터 / 미연결 / 오류로 나눠 보고. ★
1. **테이블 설계안**: 2장 제안을 바탕으로 컬럼·키·RLS 정책을 SQL 마이그레이션 초안으로 작성. ★
2. **Supabase 프로젝트 생성**(주완이 대시보드 또는 CLI) -> 마이그레이션 적용.
3. **적재 스크립트**: `policies_all.json` -> 정책·공고 테이블. 1차안 28건부터. `plcyNo` 기준 upsert라 다시 실행해도 중복이 생기지 않게 한다. API에 없는 7건은 `policy_candidates_v0_1.csv` 기준 수기 입력 형식을 제안. ★
4. **적재 검증**: 건수, `plcyNo` 중복, 후보별 매칭(개별 18·묶음 3·없음 7)이 매칭표와 같은지, 3장 품질 문제 1~10 처리 결과.
5. **프론트 공유**: 타입 생성, 조회 예시, 테이블 설명.
6. **AI 단계**: 모델 결정 ★ -> pgvector 컬럼 -> 임베딩 배치 -> 조건 초안 추출(검수 상태 '초안'으로 저장). 실험실 클라우드는 1개월 고정이라 시연(11/30)까지 쓰려면 시작 시점을 맞춘다.
